# Security policy

Adamant holds live advertising credentials — Google Ads OAuth tokens, a Sklik API
token, social publishing tokens — and the account data pulled through them. A
vulnerability here is not "someone reads a demo dashboard"; it is someone
spending an advertiser's budget. Please treat it accordingly, and so will we.

## Reporting a vulnerability

**Do not open a public issue.**

Report privately via GitHub's [private vulnerability
reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)
on this repository (Security → Report a vulnerability), or by email to the
address in the repository's profile.

Useful reports include: affected version or commit, deployment shape (hosted
cloud or self-hosted; `LOCAL_DB` or Firestore), reproduction steps, and what an
attacker gets. A proof of concept is welcome; testing against somebody else's
live instance is not. Never paste a real API key, OAuth token or service-account
JSON into the report — describe it, and rotate it.

**Response targets:** acknowledgement within 3 working days, an initial
assessment within 10, a fix or documented mitigation within 30 for anything
rated high or critical. If a fix will take longer, you'll get the reason and a
date rather than silence.

Please give us a reasonable window to ship a fix before disclosing publicly. We
will credit you in the advisory unless you'd rather we didn't.

## Supported versions

This is a young project on a single release line. Security fixes land on `master`
and in the current deployment. There are no maintained back-branches yet; if you
need one, that conversation belongs in an issue.

## Scope

In scope: this repository's application code, the API route handlers under
`src/app/api/`, the cron endpoints, the store seams, the LLM chokepoint and its
BYOM key handling, and the default configuration they ship with.

Out of scope: findings that depend on a deliberately insecure configuration the
docs already warn about (see below), vulnerabilities in third-party providers
(Google Ads, Sklik, Gemini, Leonardo, Meta, LinkedIn, Resend), the deliberately
public demo data under `test-llm/` and the seeded demo projects, and reports
generated by a scanner with no demonstrated impact.

## Things that are the operator's job, not a vulnerability

A self-hosted install is only as safe as its configuration. These are documented
behaviours, not bugs — see
[`docs/open-source/self-hosting.md`](./docs/open-source/self-hosting.md):

- **`AUTH_SECRET` unset means no valid sessions.** There is no default. Generate
  one per install; never reuse the value from another deployment.
- **`CATALOG_TOKEN_SECRET` unset means warehouse/ERP tokens fall back to
  `AUTH_SECRET` for encryption at rest** (`src/lib/inventory/token-crypto.ts`).
  That works, but it couples token ciphertext to session-secret rotation:
  rotating `AUTH_SECRET` makes stored tokens undecryptable. Set a dedicated
  secret before you store any connector token.
- **`BYOM_KEY_SECRET` unset means the same fallback for user-supplied model
  keys** (`src/lib/llm/keys/crypto.ts`). Same reasoning; set it explicitly.
- **`CRON_SECRET` unset means the cron endpoints are disabled, not open.**
  `src/lib/cron-auth.ts` fails closed and compares constant-time. Scheduled
  syncs, reports and social publishing simply never run. That is a
  configuration state, not a compromise.
- **`AI_GLOBAL_DAILY_CEILING` fails *open* by default.** If the counter store is
  unreachable, paid calls proceed. Set `AI_CEILING_FAIL_CLOSED=1` if you would
  rather lose the feature than the budget. Setting the ceiling to `0` disables
  it entirely.
- **`ADMIN_EMAILS` fails closed.** With it unset, nobody is an admin — the
  operator telemetry surfaces are simply unreachable.
- **`DEV_AUTH=true` bypasses login entirely.** It is ignored when
  `NODE_ENV=production` (`src/auth.ts`), and it belongs only in `.env.local`.
  Never set it on a deployment reachable from the internet.
- **No TLS is provided by the app.** Terminate TLS in front of it, and set
  `TRUSTED_PROXY` only when a proxy you control actually rewrites the client-IP
  headers — trusting them off-platform lets a caller forge their own rate-limit
  identity (`src/lib/ai/rate-limit.ts`).

## Automated guardrails we run

- **Secret scanning** — `.gitignore` excludes `.env*` (except `.env.example`),
  `*.pem` and `/.data`; a pre-commit hook runs on staged files. A full-history
  `gitleaks` / `trufflehog` sweep is part of the go-public checklist in
  [`docs/open-source/impact.md`](./docs/open-source/impact.md) and will become a
  CI job at that point. Any hit is a hard fail.
- **Typecheck, lint and build** on every change — `npm run check:ci`, which also
  runs the unit suite and the LLM proof gate (`scripts/llm-gate.mjs`). The gate
  is what prevents an un-reviewed model call site from reaching the tree.
- **Dependency scanning** — GitHub Dependabot alerts on the default branch.
  There is no blocking severity gate yet; that is a known gap, stated here
  rather than left blank.
- **SAST** — not applicable today. ESLint's security-relevant rules are the only
  static analysis in CI. Stated explicitly so it is a visible gap, not an
  invisible one.
- **Container image scanning / SBOM / signed artifacts** — not applicable: this
  repo publishes no images or packages yet. Self-host packaging is a design in
  [`docs/open-source/self-hosting.md`](./docs/open-source/self-hosting.md), not
  a shipped artifact.

## Where secrets come from

Secrets are read from the environment at runtime — Vercel project environment
variables for the hosted deployment, a `.env` file or the orchestrator's secret
store for a self-hosted one. They are never committed, never pasted into an issue
or a PR description, and never included in a prompt or a log line. The LLM
chokepoint logs operation names, token counts and cost — not credentials.

If a secret does reach the remote: **rotate it first**, then clean the history.
Deleting the file is not a fix — the value is in the history and in every clone.

## Hardening worth knowing about

- **Tenancy is structural, not checked.** The tenant key embeds the user id
  (`u_{userId}_proj_{projectId}`), so a cross-user IDOR would require forging a
  session rather than guessing an id.
- **All AI routes to a key you control.** In a self-hosted install there is no
  Adamant-hosted inference in the path, and the local engines (Claude CLI on a
  subscription, Ollama via `OLLAMA_BASE_URL`) need no key at all. With no
  provider configured, every operation returns its deterministic demo result.
- **Nothing phones home by default.** Sentry initialises only with a DSN, in
  errors-only mode with no tracing and no source-map upload. LightTrack mirrors
  LLM calls only when `LIGHTTRACK_PROJECT` or `LIGHTTRACK_KEY` is set, and its
  default endpoint is loopback. There is no analytics SDK in the tree.
- **Paid routes are guarded server-side** — a per-user daily quota
  (`src/lib/usage.ts`) plus a durable per-IP window and a global daily spend
  ceiling (`src/lib/ai/durable-limit.ts`). Both are cost controls on the
  operator's own provider bill.
